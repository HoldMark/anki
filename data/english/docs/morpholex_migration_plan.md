Статус: **выполнено**. Перенос запущен и завершён успешно:

## 1. Лист `Presentation` — глоссарий колонок

Лист описывает смысл колонок, которые встречаются на "словных" листах (`0-1-0` … `3-1-0`).
Реальные данные на листе занимают только колонки C–D, строки 1–24, дальше пусто.

| Колонка                                                                               | Описание                                                                     |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `ELP_ItemID`                                                                          | ID слова из Complete ELP (English Lexicon Project)                           |
| `Word`                                                                                | Слово                                                                        |
| `POS`                                                                                 | Часть речи (может быть несколько через `\|`, например `NN\|JJ`)              |
| `Nmorph`                                                                              | Количество морфем в слове                                                    |
| `PRS_signature`                                                                       | Prefix-Root-Suffix сигнатура, например `"0,1,0"`                             |
| `MorphoLexSegm`                                                                       | Морфологическая сегментация слова с каноничными аллморфами каждой морфемы    |
| `PREF_PFMF`                                                                           | % более частотных слов в морфологической семье (для префикса)                |
| `PREF_FamSize`                                                                        | Размер морфологической семьи (для префикса)                                  |
| `PREF_Freq_HAL`                                                                       | Суммарная частота морфемы по HAL-корпусу (для префикса)                      |
| `PREF_P`                                                                              | Приближение вероятности того, что морфема встречается в hapax (для префикса) |
| `PREF_P*`                                                                             | Приближение вероятности hapax, содержащего морфему (для префикса)            |
| `PREF_length`                                                                         | Длина префикса в буквах                                                      |
| `ROOT_PFMF`                                                                           | То же, что `PREF_PFMF`, но для корня                                         |
| `ROOT_FamSize`                                                                        | То же, что `PREF_FamSize`, но для корня                                      |
| `ROOT_Freq_HAL`                                                                       | То же, что `PREF_Freq_HAL`, но для корня                                     |
| `SUFF_PFMF` / `SUFF_FamSize` / `SUFF_Freq_HAL` / `SUFF_P` / `SUFF_P*` / `SUFF_length` | Аналогично префиксу, но для суффикса                                         |

Важно: для `ROOT` у авторов датасета **нет** `P`, `P*`, `length` — эти три метрики есть только у префиксов и суффиксов. Это подтверждается и в реальных листах (там нет колонок `ROOTn_P`, `ROOTn_P*`, `ROOTn_length`).

Также лист поясняет назначение остальных листов книги:
- Листы 2–33 (в нашей нумерации — `0-1-0` … `3-1-0` и `0-0-0`) — по одному листу на каждую PRS-сигнатуру.
- Лист `0-0-0` — 6 слов без корня (стяжения вроде `ain't`, `won't`) — **не переносим**, как и попросили.
- `All prefixes` / `All suffixes` / `All roots` — сводные списки морфем по всей базе. Переносим только `All roots` (по ТЗ).

Этот глоссарий **не переношу в БД отдельной таблицей** — он статичный и служит только документацией. Зафиксирую его как docstring/комментарий в самом скрипте переноса, чтобы было видно, что означает каждая колонка.

## 2. Структура "словных" листов (`0-1-0` … `3-1-0`)

Имя листа = PRS-сигнатура через дефис (число префиксов-корней-суффиксов), например `1-2-2` = 1 префикс, 2 корня, 2 суффикса.

Все 29 листов имеют одинаковую **логику** колонок:

1. 6 базовых колонок (одинаковые везде): `ELP_ItemID, Word, POS, Nmorph, PRS_signature, MorphoLexSegm`
2. Блок из 6 колонок на каждый `PREFn` (n = 1..3): `PFMF, FamSize, Freq_HAL, length, P, P*`
3. Блок из 3 колонок на каждый `ROOTn` (n = 1..4): `PFMF, FamSize, Freq_HAL`
4. Блок из 6 колонок на каждый `SUFFn` (n = 1..4): `PFMF, FamSize, Freq_HAL, length, P, P*`

Из-за этого **ширина листов разная** — от 12 колонок (`0-1-0`, один корень и ничего больше) до 39 колонок (`1-1-4` / `0-1-4`, где 4 суффикса). Первая строка каждого листа — заголовки, дальше — данные. Объём данных тоже сильно разный: от 1 строки (`3-1-0`, `0-3-2`, `0-4-0`, `1-2-3`) до ~31 000 строк (`0-1-0`).

Отдельно — лист `0-1-0` устроен немного иначе технически: перед `ELP_ItemID` там 3 пустых столбца (A, B, C), заголовок начинается с колонки D.
На остальных листах заголовок начинается с колонки A. Это не влияет на смысл данных, но означает, что **скрипт обязан искать колонки по названию заголовка,
а не по индексу/букве столбца** — иначе на листе `0-1-0` он либо промахнётся мимо данных, либо упадёт.

## 3. Лист `All roots`

Отдельный, не связанный напрямую со словными листами справочник: 15 471 строка данных,
3 колонки — `morpheme, family_size, HAL_freq`.
Формат `morpheme` совпадает с нотацией корня в `MorphoLexSegm` (например `"(strong)"`).

## 4. Проблемы файла и как их решаем

### 4.1. Переменная ширина листов → почему нужны ДВЕ таблицы, а не одна широкая

Сначала подтверждаю: понимание верное. Каждый лист — это фиксированная комбинация
«сколько префиксов / сколько корней / сколько суффиксов» (она же — имя листа). Все слова
на этом листе имеют ровно такую комбинацию, и под каждый *экземпляр* морфемы в этой
комбинации выделен свой блок колонок: на листе `2-1-0` (2 префикса, 1 корень, 0 суффиксов)
будут колонки `PREF1_*`, `PREF2_*`, `ROOT1_*`. На листе `1-2-3` (1 префикс, 2 корня,
3 суффикса) — уже другой набор: `PREF1_*`, `ROOT1_*`, `ROOT2_*`, `SUFF1_*`, `SUFF2_*`, `SUFF3_*`.
Именно поэтому у разных листов разное число колонок (12–39).

**Конкретный пример трансформации.** Возьмём слово `impressionistically` с листа `1-1-4`
(1 префикс, 1 корень, 4 суффикса). В Excel это одна строка на 39 колонок:

| ELP_ItemID | Word                | ... | PREF1_PFMF | ... | ROOT1_PFMF | ... | SUFF1_PFMF | ... | SUFF2_PFMF | ... | SUFF3_PFMF | ... | SUFF4_PFMF | ... |
| ---------- | ------------------- | --- | ---------- | --- | ---------- | --- | ---------- | --- | ---------- | --- | ---------- | --- | ---------- | --- |
| 22403      | impressionistically | ... | 96.08      | ... | 94.44      | ... | 97.56      | ... | 95.66      | ... | 94.37      | ... | 86.88      | ... |

После переноса это превращается в: **1 строку** в `morpholex_words` (сама карточка слова:
`elp_item_id=22403, word="impressionistically", ...`) и **6 строк** в `morpholex_morphemes`
(по одной на каждый блок `PREFn_*/ROOTn_*/SUFFn_*` из исходной строки):

| word_id | morpheme_type | position | pfmf  | ... |
| ------- | ------------- | -------- | ----- | --- |
| ↳22403  | PREF          | 1        | 96.08 |     |
| ↳22403  | ROOT          | 1        | 94.44 |     |
| ↳22403  | SUFF          | 1        | 97.56 |     |
| ↳22403  | SUFF          | 2        | 95.66 |     |
| ↳22403  | SUFF          | 3        | 94.37 |     |
| ↳22403  | SUFF          | 4        | 86.88 |     |

То есть каждый именной блок колонок (`SUFF3_*` и т.п.) становится не колонкой, а **строкой**
с указанием типа (`SUFF`) и порядкового номера (`3`) в колонках `morpheme_type`/`position`.
Это стандартный приём (unpivot / переход от "широкого" формата к "длинному").

**Почему не оставить как в Excel:**

- **Вариант А — 29 отдельных таблиц** (по одной на лист, `morpholex_0_1_0`, `morpholex_1_2_2`, ...). Технически просто, но бессмысленно для использования: чтобы найти все суффиксы слова "cats" пришлось бы заранее знать, в какой из 29 таблиц оно лежит, а у каждой таблицы — свой набор колонок (`SUFF1_*` в одной, `SUFF1_*..SUFF4_*` в другой). Любой запрос "покажи мне все слова с суффиксом X" превращается в `UNION` из 29 таблиц.

- **Вариант Б — одна общая широкая таблица** на все 29 листов, с колонками на максимальное количество морфем: `PREF1_*..PREF3_*` (18 колонок) + `ROOT1_*..ROOT4_*` (12 колонок) + `SUFF1_*..SUFF4_*` (24 колонки) = 54 колонки + 6 базовых = 60 колонок. Проблема: у слова с сигнатурой `0,1,0` (только один корень, как "ALF") заполнены будут всего 9 из 60 колонок, а **51 колонка будет `NULL`**. У большинства слов в базе (сигнатура `0-1-0` — это 31 117 из общего числа строк, самый большой лист) будет именно такая ситуация. Это:
  - тратит место и создаёт "пустую" таблицу, где не видно с первого взгляда, сколько реально морфем у слова;
  - хрупко: если в датасете вдруг встретится слово с 5 суффиксами (в этом файле максимум 4, но в принципе такое бывает у длинных производных слов), придётся руками добавлять `SUFF5_*` колонки и переписывать схему;
  - неудобно для запросов: "дай мне список всех суффиксов слова" превращается в `SELECT SUFF1_PFMF, SUFF2_PFMF, SUFF3_PFMF, SUFF4_PFMF ... WHERE SUFF1_PFMF IS NOT NULL OR SUFF2_PFMF IS NOT NULL ...` вместо простого `WHERE morpheme_type='SUFF'`.

**Предлагаемое решение — нормализация в две связанные таблицы:**

- **`morpholex_words`** — "родительская" сущность, одна строка на слово. Хранит то, что не повторяется: собственный `id`, `elp_item_id`, само слово, часть речи, число морфем, сигнатура, строка сегментации.
- **`morpholex_morphemes`** — "дочерняя" сущность, одна строка **на каждый блок `PREFn_*/ROOTn_*/SUFFn_*` конкретного слова** (см. пример выше). У слова "cats" (`0,1,0`) будет 1 строка в этой таблице (один корень). У слова "impressionistically" (`1,1,4`) — 6 строк, как показано выше. Колонки: `word_id` (ссылка на строку в `morpholex_words`), `morpheme_type` (`PREF`/`ROOT`/`SUFF`), `position` (1, 2, 3...), и сами метрики `pfmf, fam_size, freq_hal, length, p, p_star` (для `ROOT` последние три всегда `NULL` — это ожидаемо и нормально, т.к. на листах у `ROOTn` этих колонок в принципе нет).

Итог: вместо 60 колонок с кучей `NULL` — компактная таблица, где у каждого слова ровно столько строк-морфем, сколько у него реально есть, и любой новый максимум морфем (хоть 5, хоть 10) добавляется без изменения схемы — просто больше строк в `morpholex_morphemes`.

### 4.2. Разное написание PRS-сигнатуры

В данных сигнатура пишется через запятую (`"0,1,0"`), в имени листа — через дефис (`"0-1-0"`). Обе формы храним: `prs_signature` (как в ячейке, для сверки) плюс распарсенные `n_prefix, n_root, n_suffix` (из имени листа) для удобной фильтрации (`WHERE n_suffix = 2`).

### 4.3. Аномалия в данных на листе `1-2-2`

При выборочной проверке обнаружена строка (`ELP_ItemID = 16854`, слово `multiplications`), где числа в блоке `SUFF1_*` по порядку величины не похожи на ожидаемые (`PFMF` — обычно 0–100%, а тут крошечное число похожее на `P`; `length` — обычно 1–10 букв, а тут число в тысячах). Проверено через точное обращение к диапазону ячеек — это не баг чтения, а особенность самого исходного Excel-файла (известная проблема академических датасетов такого рода — где-то при сборке файла авторами могла съехать формула/копирование для отдельных строк).

**Решение**: не пытаемся "чинить" или валидировать по правдоподобию значений — это не наша задача и рискованно (можем исказить данные, которые на самом деле корректны, просто нетипичны). Переносим значения как есть (в SQLite колонки метрик — `REAL`, он не типизирован жёстко, так что и "нормальные", и "странные" по величине числа лягут без ошибок), а каждую такую строку фиксируем в едином журнале проблем — см. 4.6.

### 4.4. Уникальность `ELP_ItemID` по всем 29 листам

Предполагаю, что `ELP_ItemID` — глобальный ID слова из ELP и уникален по всей книге (каждое слово имеет ровно одну PRS-сигнатуру и попадает ровно на один лист). `ELP_ItemID` **не делаю первичным ключом таблицы** — вместо него у `morpholex_words` собственный surrogate `id INTEGER PRIMARY KEY AUTOINCREMENT`, а `elp_item_id` хранится обычной колонкой (индексированной, но без `UNIQUE`).

Проверку уникальности всё равно делаем: перед вставкой скрипт собирает все строки со всех 29 листов, группирует по `elp_item_id` и ищет группы с более чем одной строкой. Если находит — каждая такая строка фиксируется в едином журнале проблем (см. 4.6) с `issue_type="duplicate_elp_item_id"`. Сама вставка при этом не падает и не блокируется — дубликаты переносятся в БД как обычные строки (у каждой свой surrogate `id`), т.к. решать судьбу дублей (что оставить, что убрать) — отдельная задача не в рамках этого переноса.

### 4.5. `POS` с несколькими значениями

Некоторые слова имеют составной `POS` (например `"NN|JJ"` — слово может быть и существительным, и прилагательным). Отдельную таблицу под это не делаем (не входит в задачу и раздувает схему без явной необходимости) — храним как есть строкой в `morpholex_words.pos`.

### 4.6. Устойчивость переноса к проблемным строкам/значениям

Задача: если в одной строке (как в 4.3) или в одном листе что-то не так, это **не должно останавливать перенос остальных ~90 000 строк**, и по каждой проблеме сразу должно быть понятно, *в чём именно* она — чтобы не открывать заново Excel и не разбираться с нуля, если разбор откладывается на потом.

Решение — единый журнал проблем `data/english/morpholex_import_issues.csv` и построчная обработка с перехватом ошибок:

- Каждая строка каждого листа обрабатывается в своём `try/except`. Если что-то идёт не так (не удалось привести значение к числу, неожиданная структура строки и т.п.) — строка **не прерывает выполнение скрипта**, а целиком пропускается, и по ней в журнал пишется запись.
- Запись в журнале — не просто "проблема была", а сразу с диагнозом: `source_sheet, row_number, elp_item_id, word, issue_type, reason, raw_row` — где `issue_type` — короткий код проблемы (`value_out_of_range`, `duplicate_elp_item_id`, `unparseable_value`, `row_column_mismatch` и т.п.), а `reason` — человекочитаемое пояснение с конкретными числами/именами колонок (например: `"SUFF1_PFMF=0.0000264682, ожидался диапазон 0..100"`), `raw_row` — исходные значения строки как есть (на случай, если потребуется свериться руками).
- Такой журнал даёт две вещи сразу: и сам факт проблемы, и её причину — при повторном обращении к вопросу не нужно заново лезть в Excel и вычислять, что именно не так, достаточно прочитать `reason`.
- Скрипт в конце выводит сводку: сколько строк обработано успешно, сколько ушло в журнал проблем и с разбивкой по `issue_type`.
- Это не отменяет идемпотентность (п. 6): при повторном запуске журнал переписывается заново (`w`-режим, не дозапись), т.к. пересчитывается с нуля вместе с таблицами.

## 5. Итоговая схема БД

```sql
CREATE TABLE morpholex_words (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    elp_item_id     INTEGER NOT NULL,  -- ID из Complete ELP; см. 4.4 про дубликаты
    word            TEXT NOT NULL,
    pos             TEXT,
    nmorph          INTEGER,
    prs_signature   TEXT,           -- как в ячейке, напр. "1,2,2"
    morpholex_segm  TEXT,
    n_prefix        INTEGER NOT NULL,  -- распарсено из имени листа
    n_root          INTEGER NOT NULL,
    n_suffix        INTEGER NOT NULL,
    source_sheet    TEXT NOT NULL,     -- напр. "1-2-2", для трассировки к исходному Excel
    imported_at     TIMESTAMP NOT NULL
);
CREATE INDEX idx_morpholex_words_word ON morpholex_words(word);
CREATE INDEX idx_morpholex_words_elp_item_id ON morpholex_words(elp_item_id);

CREATE TABLE morpholex_morphemes (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    word_id         INTEGER NOT NULL REFERENCES morpholex_words(id),
    morpheme_type   TEXT NOT NULL CHECK (morpheme_type IN ('PREF','ROOT','SUFF')),
    position        INTEGER NOT NULL,  -- 1, 2, 3...
    pfmf            REAL,
    fam_size        REAL,
    freq_hal        REAL,
    length          REAL,   -- NULL для ROOT
    p               REAL,   -- NULL для ROOT
    p_star          REAL,   -- NULL для ROOT
    UNIQUE (word_id, morpheme_type, position)
);
CREATE INDEX idx_morpholex_morphemes_word_id ON morpholex_morphemes(word_id);

CREATE TABLE morpholex_root_stats (
    morpheme        TEXT PRIMARY KEY,   -- напр. "(strong)"
    family_size     INTEGER,
    hal_freq        INTEGER
);
```

Никаких FK на существующие таблицы (`cambridge_words`, `anki_notes` и т.д.) не делаем — сопоставление `word` с уже существующими словами ненадёжно (регистр, формы слова) и не входит в задачу; таблицы `morpholex_*` — самостоятельный справочник.

## 6. Реализация (после согласования)

- Скрипт: `data/english/build_morpholex_tables.py`.
- Зависимость: `openpyxl` (сейчас не установлен в `venv/`, нужно добавить).
- Перед прогоном — бэкап `sync.sqlite` в `backups/sync.sqlite.bak-<timestamp>-morpholex`, по аналогии с существующими бэкапами.
- Скрипт идемпотентен: `DROP TABLE IF EXISTS` для всех трёх таблиц перед созданием — повторный запуск не плодит дубликаты.
- Листы читаются по названию заголовка (см. 4.1 про `0-1-0`), не по индексу колонки.
- Построчная обработка с перехватом ошибок и единым журналом `morpholex_import_issues.csv` — см. 4.6. Одна плохая строка не прерывает перенос остальных.
- В конце — отчёт: сколько слов/морфем перенесено по каждому листу, сколько строк ушло в журнал проблем и с разбивкой по типам.
- `docs/schema.md` дополню разделом про `morpholex_*` таблицы после реализации.
