# План: инструмент синхронизации Anki ⇄ Cambridge Dictionary

## Назначение

Отдельный CLI-инструмент, живущий в этой директории (`sync/`), который:

1. Зеркалирует данные записей (notes) Anki в локальную базу SQLite (`sync.sqlite`, находится внутри этого проекта и добавлена в `.gitignore`).
2. Читает справочные данные Cambridge Dictionary, которые пишет в эту же БД `lexicon-scraper` — независимый, отдельно запускаемый инструмент, — в собственных таблицах, полностью отдельных от зеркала Anki.
3. Предлагает предположительные (candidate) связи между записями Anki и справочными записями Cambridge и позволяет подтверждать эти связи (вручную либо автоматически, когда связь однозначна).
4. Дополняет существующие записи Anki небольшим, явно ограниченным, но расширяемым набором полей, вычисляемых из БД (для начала — только `cefr`, в будущем добавятся другие поля) — никогда не трогая поля, которыми уже владеет человек в Anki (`word`, `definition`, `part_of_speech`, `examples` и т.п.).

Anki — источник истины для собственного контента. БД зеркалирует его для справки и дополняет только то, что ей явно разрешено. Этот инструмент никогда не создаёт новые записи в Anki, никогда не запускается автоматически/по расписанию и не предоставляет MCP-сервер — это исключительно CLI, запускаемый вручную. Полную схему и список команд см. в `architecture.ru.md`.

## Почему именно так

- У записей Anki уже есть два скрытых, пустых поля — `_system_hash` и `_system_note_uuid` — подготовленных в типе заметки, но пока нигде не используемых. **`_system_note_uuid` был добавлен намеренно как устойчивый якорь идентичности именно для того, чтобы этот инструмент не зависел от собственного внутреннего id записи в Anki** для долгосрочной идентичности (этот id гарантированно стабилен только для обращения к записи *прямо сейчас* через AnkiConnect — это не устойчивый ключ во времени/между импортами). Этот план строится вокруг заполнения `_system_note_uuid`/`_system_hash` как первого, независимого от БД шага, и рассмотрения именно uuid, а не id записи Anki, как истинного долгосрочного якоря, как только он появляется.
- **Записи в Anki не привязаны к колоде — привязаны карточки.** Одна и та же запись одновременно встречается в нескольких соседних колодах (`1_english::without_group::definition`, `::typing`, `::word`, `::typing_sentence`), каждая из которых показывает свой шаблон карточки поверх одних и тех же данных записи (проверено вживую: три записи "thick" одинаково присутствуют в `definition`, `typing` и `word`). Колода используется здесь только как удобный способ выбрать набор записей через поиск AnkiConnect — это не устойчивый атрибут самой записи.
- Данные Cambridge были импортированы в Anki лишь частично, а записи Anki с тех пор независимо правились вручную — `word`, `definition`, `part_of_speech` и `examples` вполне могут меняться внутри Anki со временем. **Транскрипция (произношение) гораздо менее подвержена изменениям, чем текст definition/sense**, поэтому она используется как основной ключ для предложения предположительных связей Anki↔Cambridge, и такие связи не нужно перепроверять при каждом цикле синхронизации, в отличие от сопоставления по тексту определения. Поскольку даже сопоставление по транскрипции не гарантирует связь 1:1 (одна транскрипция может покрывать несколько значений/sense), связи всегда сначала предлагаются как *кандидаты*, и только затем явно подтверждаются (вручную либо автоматически, только если у записи ровно один однозначный кандидат).
- `lexicon-scraper` заполняет справочные таблицы Cambridge напрямую и независимо — он не вызывается из CLI этого инструмента. Этот проект только определяет и читает эту схему.
- Пользователь будет продолжать добавлять новые записи в Anki со временем через собственный процесс импорта (вне этого инструмента). Этот план включает явный шаг обнаружения записей, у которых ещё нет `_system_hash`/`_system_note_uuid`, чтобы их можно было найти, проштамповать и подтянуть отдельным, контролируемым проходом, а не просто считать, что таких случаев не будет.
- В существующем коде репозитория (`addons/grammar_drill/src/db/`) уже сложилась своя конвенция для слоя БД (`Database` / `Table` / `Service`, без ORM) и своя конвенция доступа к Anki через AnkiConnect (`mcp/src/anki_client.py`) — этот инструмент следует обеим. Конфигурация же следует шаблону "простой `pydantic.BaseModel` + `python-dotenv`", используемому в собственном файле пользователя `autotest_api/src/config/load_env.py` (функция-строитель, вручную читающая `os.environ.get(...)` в `BaseModel`, а не `pydantic-settings`).

## Этапы

### Этап 1 — Каркас проекта

- `pyproject.toml`, `Makefile`, `requirements.txt`, `.env`, `.gitignore` (обязательно должен включать `sync.sqlite`, `.env`, `venv/`, `__pycache__/`).
- `main.py` как точка входа CLI на `typer`.
- `src/config/load_env.py`: `load_dotenv()` во время импорта, простой класс конфигурации на `pydantic.BaseModel` и функция-строитель `get_config()`, явно читающая `os.environ.get(...)` — повторяя существующий шаблон конфигурации пользователя из `autotest_api`, а не `pydantic-settings`.
- Общий логгер (файл + stdout), используемый всеми командами как для журналирования отдельных действий, так и для отчёта о прогрессе массовых операций (см. Этап 8).

### Этап 2 — Слой БД

- `src/db/database.py`: класс `Database`, обёртка над `sqlite3` (`execute`/`query`, идемпотентный `create_tables`) — тот же подход, что и в `grammar_drill`.
- `src/db/tables/_table.py`: базовый класс `Table`.
- Классы таблиц для зеркала Anki (`anki_notes`) и справочных таблиц Cambridge (`cambridge_words`, `cambridge_parts_of_speech`, `cambridge_transcriptions`, `cambridge_senses`, `cambridge_definitions`, `cambridge_examples`), а также `note_definition_links`. Этот проект создаёт и владеет всей этой схемой, включая таблицы `cambridge_*` — `lexicon-scraper` в них пишет, но саму схему определяет этот проект.
- Соответствующие классы `Service`. Важно: в отличие от `WordService` из `grammar_drill` (который делает get-or-create по совпадению содержательных полей), поиск строки `anki_notes` идёт в первую очередь по `system_note_uuid`, когда он уже есть (устойчивый якорь), с запасным вариантом по `anki_note_id` — никогда по совпадению `word`/`definition`/`part_of_speech`/`examples`, поскольку эти поля вполне могут меняться внутри Anki.

### Этап 3 — Доступ к Anki

- `src/anki_client.py`: тот же контракт `invoke(action, **params)`, что и в `mcp/src/anki_client.py`, продублированный здесь, чтобы `sync/` оставался самодостаточным.
- `src/anki/notes.py`: `get_notes(deck)`, `get_notes_fields(ids)`, `update_note_fields(id, fields)`, плюс помощник для поиска записей с пустым полем `_system_note_uuid` (синтаксис поиска по пустому полю в AnkiConnect) для Этапа 4.

### Этап 4 — `discover-new` (только чтение, находит свежеимпортированные записи)

- Пользователь будет продолжать импортировать новые записи в Anki со временем, вне этого инструмента. У новых записей ещё не будет `_system_hash`/`_system_note_uuid`.
- `discover-new [--deck NAME]` ищет в выбранной колоде записи с пустым `_system_note_uuid` и выводит их (количество + id записи + слово) — без записи. Это чисто шаг для наглядности перед запуском `stamp`.

### Этап 5 — `stamp` (Anki → Anki, без участия БД)

Выполняется **до** любого заполнения БД и по своей природе безопасен для повторного запуска по всей колоде в любой момент (в том числе после обнаружения новых записей):
- Вычислить хеш контента из только что полученных живых полей записи (не из зеркала БД).
- Сгенерировать `system_note_uuid`, только если он сейчас пуст (если не указан `--force`) — это и есть значение-якорь, генерируемое один раз и никогда не перегенерируемое впоследствии, кроме как через явный force.
- Записать оба поля, `_system_hash` и `_system_note_uuid`, обратно через `update_note_fields`, пропуская поле, если оно уже не пусто, если не указан `--force`.
- Поддерживает `--dry-run` для предпросмотра количества записей — на самом первом запуске стоит ожидать, что будет затронут весь выбранный набор записей, а на последующих запусках — только вновь обнаруженное подмножество.

### Этап 6 — `pull` (Anki → БД, устойчивый постатейный upsert)

- Получить все записи выбранной колоды (уже проштампованные).
- Обрабатывать **по одной записи за раз**, а не сплошным удалением и массовой вставкой. Искать существующую строку зеркала в первую очередь по `system_note_uuid` (чтобы запись сохраняла идентичность, даже если её `anki_note_id` когда-либо изменится), с запасным вариантом по `anki_note_id` для редкого случая, когда uuid ещё не проставлен. Проблема с одной записью не должна прерывать весь запуск — такая строка помечается `sync_status='error'` с понятным человеку сообщением в `sync_issue`, журналируется, и обработка продолжается.
- **Этап ручной проверки**: перед применением каждой изменившейся строки показывается разница "было/стало" (какие поля изменились, старое → новое значение) для подтверждения. Можно пропустить через `--skip-review` или флаг конфигурации `REQUIRE_REVIEW=false` — тогда изменения применяются без паузы.
- Журналирует и выводит прогресс массовых запусков: `[текущий/всего] (процент%) — запись <id>: создана / обновлена / без изменений / ошибка`, плюс итоговую сводку.

### Этап 7 — Данные Cambridge (внешний процесс, вне кода этого инструмента)

- `lexicon-scraper` запускается независимо и пишет напрямую в таблицы `cambridge_*` этого проекта (схема определена на Этапе 2). Этот проект не содержит команды импорта и сам не вызывает `lexicon-scraper`.

### Этап 8 — `match` / `confirm` / `review`

- `match`: предлагает **кандидатные** связи между `anki_notes` и `cambridge_definitions` по ключу `(word, transcription, transcription_type)` — выбрано потому, что транскрипция редко меняется, даже когда текст definition/sense правится вручную. Одна транскрипция всё ещё может покрывать несколько значений, поэтому этот шаг надёжно даёт ноль, одного или нескольких кандидатов на запись, но никогда не гарантирует единственное совпадение. Безопасно и дёшево перезапускать; нужно перезапускать заново только когда обнаружены/проштампованы новые записи или импортированы новые слова Cambridge — не при каждом `pull`.
- `confirm`: переводит конкретного кандидата в статус фактической связи, используемой при обогащении — либо явно указанной (`--note ID --definition ID`), либо автоматически для любой записи, у которой сейчас ровно один неотклонённый кандидат (`--auto-single`). На запись в любой момент существует не более одной подтверждённой связи.
- `review`: отчёт только для чтения по записям без кандидатов, записям с несколькими неразрешёнными кандидатами, ожидающими `confirm`, и по записям с `sync_status='error'` из последнего `pull`.

### Этап 9 — `enrich` (БД → Anki, ограниченно и расширяемо)

- Записывает небольшой, явно заданный набор полей из данных БД, беря их только из **подтверждённых** связей. **Пока только `cefr`**, записывается только если `cefr` в Anki сейчас пуст — построено как расширяемый реестр (имя поля → функция-резолвер значения), чтобы позже можно было добавлять новые поля без переделки команды.
- Перед записью каждого поля заново получает актуальные значения из Anki (защита от параллельной ручной правки после последнего `pull`).
- То же поведение проверки/сравнения и пропуска, что и в `pull` (Этап 6), та же защита от перезаписи непустых значений (`--force` для отключения), то же журналирование прогресса.

## Вне рамок (навсегда, а не только "пока")

- Создание новых записей Anki из данных Cambridge или чего-либо ещё — этот инструмент никогда не вызывает `addNote`.
- Автоматические или запускаемые по расписанию запуски любого рода — только CLI, запускаемый вручную.
- MCP-сервер для этого проекта — вообще не планируется, ни сейчас, ни позже.
- Любой код импорта Cambridge внутри этого проекта — это зона ответственности `lexicon-scraper`, запускаемого независимо.
- Разделение идентичности записей по колодам — записи не привязаны к колоде, поэтому `anki_notes` привязана к `system_note_uuid`/`anki_note_id`; колода — лишь механизм выбора.

## Процесс работы с новыми записями (кратко)

Внешний массовый импорт в Anki (пользователем, вне этого инструмента) → `discover-new` (посмотреть, что нового) → `stamp` (записать hash/uuid для новых записей; безопасно запускать широко) → `pull` (зазеркалить их в БД) → `match` (предложить кандидатов для новых записей) → `confirm` → `enrich`.

## Проверка (verification)

- `discover-new` сразу после свежего импорта в Anki выводит именно вновь импортированные записи и ничего уже проштампованного.
- `stamp --dry-run` на выбранной колоде `definition` сообщает об одной планируемой записи на заметку при самом первом запуске (оба поля пусты), а при последующем запуске после свежего импорта — только по вновь обнаруженным записям.
- После `stamp`, а затем `pull`, каждая зазеркаленная запись уже несёт непустые `system_hash`/`system_note_uuid`.
- Повторный запуск `pull` подряд без изменений в Anki между запусками сообщает о нуле расхождений и нуле ошибок.
- Намеренное изменение `definition` записи в Anki с последующим `pull` показывает видимую разницу "было/стало" именно по этому полю — но ранее **подтверждённая** связь Cambridge для этой записи остаётся действительной (транскрипция не изменилась), поэтому `enrich` продолжает работать без необходимости перезапускать `match`/`confirm`.
- `match` для слова, у которого одна транскрипция в Cambridge покрывает три значения, создаёт три кандидатные строки для соответствующей записи (записей); `confirm --auto-single` разрешает только те случаи, что сопоставляются 1:1, оставляя остальные для ручной проверки.
- `enrich --dry-run` сообщает о планируемой записи `cefr` только для записей с пустым `cefr` и **подтверждённой** (а не просто кандидатной) связью Cambridge.
- Удаление/порча полей одной записи (смоделированная) во время `pull` не прерывает пакетную обработку — запуск завершается, эта запись помечается `sync_status='error'`, а остальные записи обрабатываются как обычно.
